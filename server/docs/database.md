# Database

MongoDB Atlas (replica set) with Mongoose 8. Scope follows R01 V: test money only (LI-02),
no delivery company data (LI-05), SMS OTP only (FE-01), AI results are advisory only (LI-03).

## Layout and conventions

- One model per collection in `src/features/<name>/<name>.model.ts`. The collection name is
  set explicitly and equals the folder name (`rental_orders`, `wallet_transactions`, ...).
- Model files are leaf modules: they import only `mongoose`, `src/shared/` and
  `src/infrastructure/database/`. Only repositories import model files. A repository may
  import another feature's model file when a workflow needs one transaction across
  collections (e.g. accepting a rental writes `toys`, `rental_orders` and
  `order_status_history`), but never another feature's service, controller or repository.
  Cross-feature behaviour goes through a port in `src/shared/contracts/` wired by `app/`
  (e.g. `PostLedger`, implemented by `features/wallets/wallets.repository.ts`).
- Status catalogs, value catalogs and transition maps live in `src/shared/domain/`
  (`statuses.ts`, `enums.ts`, `transitions.ts`) as `as const` arrays with UPPER_SNAKE values.
  Schemas use them as `enum`; validation schemas should import the same arrays.
- Order types reuse `src/shared/contracts/order-status-change.ts` (`RENTAL`, `RESALE`,
  `DONATION`) and actor types reuse `src/shared/contracts/actor.ts`.
- Fields are camelCase. `timestamps: true` (`createdAt`, `updatedAt`); append-only and log
  collections keep `createdAt` only.
- Money is whole VND in a `Number`, validated as an integer and never negative
  (`money()` / `optionalMoney()` in `src/infrastructure/database/schema-types.ts`). Only
  ledger amounts are signed. There is no currency field.
- Every index is declared once with `schema.index(..., { name })`; no field-level
  `unique: true`. Partial filters use only equality, `$exists: true`, `$type` and `$in`
  (`$ne`/`$not` are rejected by MongoDB).
- References are `ObjectId` with `ref`. MongoDB does not check that the referenced document
  exists, so services check user-supplied references when they write. Accounts, orders,
  payments, ledger rows and dispute rulings are never hard-deleted (GB-36).
- Status changes use conditional updates (`updateOne({ _id, status: from }, ...)`) checked
  against the transition maps, and write one `order_status_history` row in the same
  transaction (GB-19).
- `syncDatabase()` in `src/app/models.ts` creates the collections, syncs the indexes and
  applies the `$jsonSchema` validator of `wallets`. Run it once per environment with a user
  that has the dbAdmin role; the database tests run it on every start.
- Seeds (both run inside `syncDatabase()`, both safe to re-run): `seedDefaultSettings()`
  inserts missing setting keys; `seedDefaultCategories()` (`features/categories/categories.seed.ts`)
  inserts the 13 starting categories of R02 (Montessori, STEM, vận động tinh, bàn cờ, nhập
  vai, ...) by slug with `$setOnInsert`, ONLY once per database: it then writes the `system_settings`
  marker `CATEGORIES_SEEDED` and skips while it exists, so it never brings back a category the
  Admin deleted (even after deleting all of them) nor undoes a rename.

## Money: wallets, ledger and escrow

- Each user has one wallet with two buckets: `available` and `held`. Paying an order moves
  the amount from `available` to `held` on the payer's wallet (simulated escrow, FE-06).
  Completing the order moves it out of `held` to the payees; a dispute simply leaves it in
  `held` until the ruling (FE-08). One `PLATFORM` wallet receives platform fees (0 unless
  configured).
- Every balance change is a `wallet_transactions` row. `postLedger` applies a posting with
  guarded `$inc` updates (a debit only matches a wallet whose bucket covers it), inside the
  caller's transaction. `$inc` bypasses Mongoose validation, so `wallets` also has a
  server-side validator (`available`, `held` >= 0).
- `payments` are VNPay/MoMo test-mode top-ups only; orders are paid from the wallet. A
  callback is applied once: the payment moves `PENDING -> SUCCEEDED` with a conditional
  update, `(gateway, gatewayTransactionNo)` is unique, and the ledger `entryKey` is unique.
- Withdrawals are simulated payouts: creating one moves money to `held`, rejecting moves it
  back, completing removes it from `held`. Only the last four account digits are stored.

### Later extensions

- `organizations`: `province`, `phone`, `ageGroups`, `logoUrl`, `description` are optional in
  the schema so earlier documents stay valid; the API requires `province` and `phone`.
- `categories.name_unique` and `organizations.name_unique` use the collation
  `{ locale: 'vi', strength: 2 }` (`vietnameseNameCollation`): "Đồ chơi gỗ" and "đồ CHƠI GỖ"
  collide, "Do choi go" does not. Queries that rely on these indexes pass the same collation.
  On an existing database, `syncDatabase()` drops and rebuilds both indexes.
- `users.dateOfBirth` (GB-07, minimum age `USER_MIN_AGE_YEARS`).
- `identity_verifications` stores `{ publicId, format }` instead of image URLs, so links are
  built only by the server (`buildPrivateImageUrl` in `infrastructure/storage/cloudinary.ts`).
- `audit_logs.target.id` is optional; `referenceKinds` includes `CATEGORY` and `ORGANIZATION`.
  Repositories write rows with `AuditLogModel.create([buildAuditLog(entry)], { session })`
  (`infrastructure/database/audit.ts`).
- `system_settings` keys `TOY_MIN_PHOTOS_RENT` (3), `TOY_MIN_PHOTOS_SALE` (4),
  `TOY_MIN_PHOTOS_DONATION` (3) and `USER_MIN_AGE_YEARS` (18); defaults are inserted by
  `seedDefaultSettings()` and never overwrite a changed value.
- `toys`: no change; `updatedAt` is the stale-edit token for moderation (the client sends the
  `updatedAt` it saw and the update filter includes it).

## Concurrency rules

- **No overlapping bookings (GB-14).** An index cannot express "date ranges do not overlap".
  `acceptRentalOrder` runs in a transaction that first increments `toys.calendarVersion`,
  then looks for another order of the toy in `ACCEPTED`, `PAID`, `SHIPPING`, `IN_USE`,
  `RETURNING` or `DISPUTED` whose range `[startDate, endDate)` overlaps, then moves the order
  `REQUESTED -> ACCEPTED`. Two concurrent accepts write the same toy document, so one of them
  conflicts, is retried and then sees the other booking. A `REQUESTED` order does not hold
  the calendar (R01 FE-05: the Owner accepts first).
- **Sell once.** The purchase transaction moves the toy `ACTIVE -> RESERVED` with a
  conditional update, and `one_active_order_per_toy` rejects a second active order.
  Cancelling sets the toy back to `ACTIVE` in the same transaction.
- **Donate once.** `one_accepted_per_toy` allows one accepted request per toy.
- **Touch writes instead of reads.** A plain read inside a transaction does not conflict with
  a concurrent write, so a transaction that depends on another document still being `ACTIVE`
  writes it conditionally (`$inc: { __v: 1 }` on `{ _id, status: 'ACTIVE' }`, timestamps
  untouched). Creating a donation request touches the toy (conflicts with an accept that
  reserves it) and, for an organization, the organization (conflicts with hide and delete);
  accepting an organization request touches the organization; approving a toy touches its
  category (conflicts with hide and delete of the category). Creating a toy, and changing the
  `categoryId` of a toy, saves the toy in a transaction that first touches its new category
  (port `saveWithActiveCategory`, wired in `app/toy-listing-dependencies.ts`); an edit that
  keeps the category does not touch it, so a toy keeps a category the Admin hid later. The
  loser is retried by `withTransaction` and then sees the new state.
- **Gateway callbacks.** See "Money" above.

## Tests

`tests/database/` runs against a one-node replica set from `mongodb-memory-server`: every
model's indexes build, enums and money validation, the unique rules above, the
case-insensitive name collation, the extensions above, the calendar
race, the sell-once race, callback replay, the wallet floor (also for writes that bypass
Mongoose) and the append-only collections.
